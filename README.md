# 剧本结构化解析 Agent

把自由格式的短剧剧本转成**结构化分镜数据**：场景 / 人物 / 台词 / 情绪 / 镜头提示，为下游内容生产提供标准化输入。

**在线体验**：（部署后填入地址，如 `https://screenplay-agent.streamlit.app`）

```
自由文本剧本  →  Agent 拆解  →  结构化数据  →  分镜 / 配音 / 剪辑
```

**当前状态**：网页版 + 命令行版均可运行。30 个单元测试全过（pydantic v1 与 v2 双版本验证）。

---

## 一、为什么需要它

短剧生产链路的第一个瓶颈永远是剧本：编剧交来的是 Word 或 txt，而分镜师要的是"第 3 场、林小满、焦虑、近景"这样的字段。

人工整理一部 80 场短剧需要 2–3 天，且漏抽台词、人物前后不一致是常态。这个 Agent 把它变成一次点击。

```
https://<你的应用名>.streamlit.app
```

**三步**：

1. 左侧填 API Key（DeepSeek / 通义 / Kimi / 智谱均支持）

**关于 API Key**：只存在你浏览器的会话内存里，刷新即失效，不上传到任何服务器。工具本身不内置 key，因为那会让任何访问者都能消耗额度。


## 四、Agent 是怎么拆任务的

```
整篇剧本
  ├─ ① 分场      一次调用，只返回标题列表（输出短、成本低）
  ├─ ② 逐场抽取  每场一次调用，只喂这一场原文（上下文聚焦）
  ├─ ③ 人物合并  一次调用，跨场去重（补回丢失的全局信息）
  └─ ④ 抽样复核  随机抽几场检查漏抽（质控闭环）
```

**为什么不做成"一次调用处理整篇"**——这是最重要的设计决策：

| 方案 | 问题 |
|---|---|
| 整篇一次调用 | 80 场剧本约 3 万字，超上下文；输出几十场容易中途截断、尾部丢失结构 |
| 逐场调用 | 可并行、单场失败只重试那一场、成本可控 |

代价是丢失跨场上下文，所以补了 ③ 做全局人物归一。

**额外优化**：原文有清晰场标（`1. 内景 咖啡馆 日`）时直接走规则切分，**省掉一次模型调用**。

## 五、质控体系（项目的核心价值）

结构化抽取的难点不是"能抽出来"，而是"抽出来的能不能用"。

### 5.1 强制 JSON + 四类容错

```python
'```json\n{...}\n```'      → 去代码围栏
'好的，结果如下：{...}'      → 截取第一个 { 到最后一个 }
'{"a":1, "b":2,}'          → 修尾逗号
'这是一段没有 JSON 的文字'    → 明确抛错，触发重试
```

### 5.2 反编造（最关键的一条）

模型很爱"合理推断"——原文只有两个人，它补一个"服务员"；台词记不清就自己编一句。这些流到下游会造成凭空多出角色、配音念了不存在的话。

```python
# 台词必须在原文中可查（归一化匹配，容忍标点差异）
"你等了很久吗？" in 原文        ✓
"这杯咖啡是我爷爷的秘方"         ✗ → 触发重试

# 人物名必须出现在原文中
"林小满" in 原文                ✓
"张三丰" in 原文                ✗ → 触发重试

# 说话人必须是本场人物（可自动修复，不重试）
dialogue.speaker ∉ characters  → 自动补进 characters
```

### 5.3 必填字段刻意收窄

```python
REQUIRED_SCENE_FIELDS = ("scene_id", "heading")   # 缺了没法分镜
REQUIRED_LINE_FIELDS  = ("speaker", "text")       # 缺了没法配音
```

不含 `intensity`、`shot_hints`，因为有合理默认值。**区分"必须有"和"可以默认"能显著减少无谓重试**——每次重试都是钱。

### 5.4 人物冲突检测

同一场出现「林小满」和「小满」，可能是同一人被抽成两个，也可能是两个角色。**只报告不自动合并**，交人工判断。

## 六、量化指标：漏抽率

"看起来对"和"实际完整"是两件事。`qa_check.py` 用**不依赖模型**的确定性方法做基准：

```
============================================================
结构化质量校验报告
============================================================
  原文场次数           : 3
  结果场次数           : 3 OK

  原文台词数           : 15
  抽取台词数           : 15
  漏抽条数             : 0 OK
  漏抽率               : 0.0% OK
  完整度               : 100.0%

  多抽条数             : 0 OK
============================================================
结论: 通过（漏抽率 ≤5%，无编造）
```

**设计要点**：校验器的台词识别规则与抽取器**独立实现**——否则就是"用抽取值验证它自己"的循环论证。

这个工具在开发中抓到一个真实 bug：抽取器会把「（快步走近）你等了很久吗？」的表演提示剥离到 `parenthetical` 字段，而校验器没做同样处理，导致每句带提示的台词被误报成"漏抽 + 编造"。修正后完整度到 100%。

## 八、人工复核闸门

网页版必须勾选「我已复核上述结果」才能下载。这不是流程冗余——结构化抽取漏抽率通常 5%–20%，直接喂给下游会返工。

CLI 版同样有闸门：

```
============================================================
结构化结果复核摘要
============================================================
  场次数           : 3
  台词总数          : 15
  漏抽率           : 0.0%
需重点复核：
  S01: 情绪未判定
============================================================

确认导出？(y/N)
```

`--yes` 可跳过，用于批处理。

## 九、离线模式不是"假数据"

没配 key 时自动进入规则引擎模式。它**读真实剧本**，用正则抽取，只是不调模型：

1. **测试不需要网络和钱**——30 个单测全部离线跑
2. **可作为对照组基线**——模型效果必须优于它才有意义
3. **演示不会因为没 key 挂掉**

局限很明确：**判断不了情绪**（全部"未判定"），**生成不了镜头提示**。这恰好是模型该赢的地方，也给出了量化验收指标。

## 十、实测数据（真实模型 vs 规则引擎）

示例剧本 `samples/demo.txt`（967 字，3 场），模型为通义千问 `qwen-plus`：

| 指标 | 规则引擎 | 真实模型 | 说明 |
|---|---|---|---|
| 场次识别 | 3 | 3 | 原文有清晰场标，规则引擎即可 |
| 台词抽取 | 15 | **16** | 差的那 1 句是叙述行内嵌台词 |
| 人物识别 | 2 | 2 | 都正确 |
| **漏抽率** | 6.25% | **0.0%** | 模型补上了内嵌台词 |
| **编造内容** | 0 | **0** | 两者都无编造 |
| **情绪判定率** | 0% | **87.5%** | 规则引擎根本做不到 |
| **情绪种类** | 0 | **4 种**（焦虑/平静/悲伤/温情） | 有区分度，不是全给一个标签 |
| **镜头提示** | 0 条 | **9 条** | 含景别、运镜、光线，原文没有的信息 |
| 重试次数 | 0 | 0 | 一次通过，无校验失败 |
| 成本 | 0 | 4 次调用 / 5,005 tokens | 约 ¥0.005 |

**关键发现**：规则引擎漏的那 1 句是

```
林小满在对面坐下，把包放在腿上，没有急着喝。（轻声）我以为你不会来。
```

这句**没有「人名：」前缀**，规则引擎按冒号切分抓不到；模型能从叙述语境里识别出这是台词并补全。这就是"用模型"的实际价值，不是"用了 LLM"这个事实本身。

**剩余 12.5% 未判定**的 2 句是「陈默。」（单字呼唤）和「我不知道。」（语义模糊）。模型保守留空而不是乱猜——符合提示词里「宁可留空也不要编造」的要求。

### 模型产出的镜头提示样例

```
[S01] 内景 咖啡馆 日   主导情绪=焦虑
  镜头: 中景 / 固定 / 林小满站在门口逆光而立，环视咖啡馆
        光线: 自然光
  镜头: 近景 / 固定 / 陈默合上笔记本，抬眼看向林小满
        光线: 侧光
  林小满: 你等了很久吗？                      [焦虑 3]
  陈默:   还好。我点了两杯，这杯应该还温着。      [平静 2]
  林小满: 我以为你不会来。                    [焦虑 4]
  陈默:   我答应过的事，一般都会做到。          [平静 3]
```

情绪强度分级（林小满 3→4，陈默 2→3）随对话推进变化，不是静态贴标签。

### 复现方式

```bash
python compare.py     # 需要设置 LLM_API_KEY
```

### 一个需要注意的现象：模型自检会误报

抽样复核（④）报告的"漏抽台词"和确定性校验（`qa_check.py`）的结论可能不一致。实测中前者报 1 条漏抽，后者证明完整度 100%。

原因是抽样复核让模型自己对比原文与抽取结果，而模型在长文本比对时容易把"已抽到的句子"误判为漏抽。

**所以两个口径的可信度不同**：

| 方法 | 性质 | 可信度 |
|---|---|---|
| `qa_check.py` | 确定性比对，规则独立实现 | **权威口径**，可用于 CI |
| 抽样复核（④） | 模型自检 | 仅作提示，需人工确认 |

设计上的教训是：**让模型检查自己的工作，不如用确定性代码检查**。抽样复核保留的价值在于它能发现"格式对但语义错"的问题（比如把旁白当台词），这是规则检查做不到的；但它的漏抽数字不能直接采信。

## 十二、已知限制

1. **长剧本未分块**：超 2 万字需按幕切分，当前处理单文件
2. **场景切分依赖标题**：无场标时规则引擎把整篇当一场
3. **人物归一较弱**：只做同名合并，跨剧集人物追踪需外部角色库
4. **情绪是单维标签**：真实表演常是"强装镇定"这类复合情绪，枚举表达不了
5. **未做跨场连续性检查**：如上一场人物在 A 地、下一场突然在 B 地
6. **网页版无并发**：Streamlit 单进程，多人同时用会排队
